# 双客户端运行验收

本清单验证现有 AI-only 路由在客户端中是否实际生效，不增加业务域名或默认捕获范围。先完成 [双客户端接入](configuration.md#dual-client-setup)，再按每台机器的真实版本验证。共享 Mihomo 内核、脚本运行成功或网页能打开，都不能单独证明完整兼容。

## 四组合与证据状态

| 验收单元 | 必须单独记录 |
| --- | --- |
| Windows + Clash Verge Rev | Windows 构建、客户端与核心版本、全局扩展及 Profile 扩展 |
| Windows + FlClash | Windows 构建、客户端与核心版本、普通 Profile 的 Script 绑定 |
| Ubuntu + Clash Verge Rev | 发行版、内核、桌面会话、安装方式、客户端与核心版本、扩展 |
| Ubuntu + FlClash | 发行版、内核、桌面会话、安装方式、客户端与核心版本、Script 绑定 |

四组合分别保存报告；macOS 和 FlClash Android 留待后续验收，不从桌面结果推断。缺设备、权限、可用浏览器或核心版本信息时保留缺口。

| 状态 | 含义 |
| --- | --- |
| PASS | 指定版本、模式和样本下有直接证据满足预期 |
| FAIL | 观察到与预期相反的结果，记录实际行为 |
| UNVERIFIED | 未执行、证据不足或环境不可用 |
| NOT_APPLICABLE | 本轮明确不适用，必须说明原因；不能代替缺环境 |

每项标注“直接观察 / 用户回传 / 未测”。所有适用项通过前，不宣称四组合运行验收完成。

## 先分清四层证据

| 层次 | 检查内容 | 不能推出的结论 |
| --- | --- | --- |
| 脚本输出 | 规则、单成员住宅组、DNS 策略、无重复注入 | GUI 已采用或真实请求经过住宅 |
| 原生核心接受 | 指定核心能解析配置、加载资源并启动 | 客户端后置覆写正确、公网 DNS 或 UDP 可用 |
| 客户端最终配置 | Profile 预览/生成文件、当前加载状态及后置设置 | 只看文件不能证明运行中核心加载了它 |
| 实际请求 | 业务命中链、解析路径、TUN/IPv6/WebRTC | 一个样本不能覆盖其他应用、协议或开关 |

独立 Mihomo 可对脱敏隔离配置使用其 `-t` 检查；关闭隔离配置的 TUN，避免占用生产端口。FlClash v0.9.2 的 `FlClashCore` 是宿主 IPC 程序，首个参数是 IPC 地址，**不能执行 `FlClashCore -t/-v/-h` 来替代检查**，也不要接管生产 IPC。其配置校验只做 RawConfig 反序列化，不等价于完整 Mihomo `-t`。其他独立核心的结果必须另列，不能冒充 FlClash 当前加载结果。[固定版本源码](https://github.com/chen08209/FlClash/blob/7fd417fb9a9a277c6a9339a8ac87f907df7c25f7/core/cmd/core/main.go#L11)、[配置校验](https://github.com/chen08209/FlClash/blob/7fd417fb9a9a277c6a9339a8ac87f907df7c25f7/core/config.go#L66)。

## 核对最终配置与业务样本

记录脚本版本/提交或摘要、当前规则模式、Profile 来源类型、挂载位置、实际启用开关、选中上游、DNS/TUN 设置和证据时间。不要上传完整配置或订阅。FlClash 必须检查运行桌面用户的配置，SSH 登录用户可能不是同一个人；配置目录由平台与安装方式决定，不假定固定路径。

逐项对比脚本输出与客户端最终配置：

- `AI-家宽` 只有 `家宽-SOCKS5`；`dialer-proxy` 指向有效机场上游，并确认运行时选择器当前值。
- 托管私网/AI 规则及原 Profile 兜底仍存在；检查规则编辑器或扩展是否前置/替换规则。
- exact/suffix DNS 策略、`AI-家宽-DNS-REGEX` 及其 policy 引用、非 AI 上游绑定、节点 bootstrap 保留；检查 `fallback`、追加 `system://` 和整张 `nameserver-policy` 被替换的情况。
- 核对最终 `find-process-mode`、顶层 `ipv6`、`dns.ipv6`、fake-IP 与 TUN 字段。脚本告警只看到传入值，不能发现全部后置覆写；进程查找关闭时不能声称进程规则已经验证。

样本从当前 [路由范围](routing-scope.md) 和开关选取，分别记录请求、规则和完整链路的脱敏摘要：

| 类别 | 示例与预期 |
| --- | --- |
| AI exact / suffix / regex | 分别选当前启用目录中的真实业务域名；区域 Vertex 覆盖正则，不用普通 Google 域名替代 |
| 认证与共享资源 | 启用的 `auth.openai.com` / `accounts.google.com` 与核心请求对比；共享静态资源按各自开关判断 |
| 非 AI 负样本 | 市场、下载、遥测、地图或存储域名留在原 Profile；排除原 Profile 自有家宽规则干扰 |
| 默认关闭功能 | `repo42.cursor.sh` 在索引开关关闭时不应被当前托管规则送入家宽；仅匹配样本不证明服务可访问 |
| LAN 与兜底 | 已知内网服务仍可用，普通非 AI 请求仍按原 Profile 规则处理 |

用实际应用请求及客户端 Connections/日志核对。显式 HTTP/SOCKS 代理探针只能证明该代理入口路径，不能代替系统应用的 TUN 验证。加载失败后仍可联网可能只是回退到原 Profile；不要把脚本抛错当成流量阻断。

## DNS 五类与私网解析

| 查询类别 | 配置预期 | 需要补充的实际证据 |
| --- | --- | --- |
| 启用的 AI | 住宅策略，包括启用的正则规则集 | 查询确实发生时的住宅 resolver/出站链 |
| 非 AI 海外 | 绑定当前 Profile 上游的 DoH | 非 AI 解析经对应机场上游 |
| 国内 | 国内 DoH，经 DIRECT | 实际 resolver 与直连路径 |
| 私网/LAN | 系统解析器 | 适用接口的内网 resolver、私有名称解析和服务访问 |
| 节点引导 | 独立 bootstrap，避免链路自解析递归 | 节点域名实际查询路径；节点全为 IP 时说明哪些查询不适用 |

上表的 AI 住宅 DNS 预期以当前生成的策略为准。`residentialDns: false` 的额外站点（如 AnyRouter）只注入家宽业务路由，刻意不注入住宅 DNS 策略；不要把这种分离判为故障或为通过验收扩大 DNS 范围。

记录查询类型、时间、缓存影响、实际 resolver 和出站证据；无法观察则 UNVERIFIED。fake-IP 的 A/AAAA 应答、SOCKS 域名转发和 Mihomo 自行查询分别记录。需要新查询时优先使用可控测试域名，不擅自清空系统缓存。普通 HTTP 出口 IP、ECS 字段、解析器地区或通用 DNS 检测站都不能证明这五类路径完整合格。浏览器独立 DoH 也要单列，不能从系统 DNS 推断。

Windows 可只读运行 `Get-DnsClientServerAddress`，按实际物理/TUN 接口识别 IPv4/IPv6 DNS，并对照网络设置中的 DHCP/静态来源。Ubuntu 先识别 resolver 管理方式；适用时检查 `resolvectl status`、`readlink -f /etc/resolv.conf` 和 NetworkManager 的 `nmcli device show`。这些输出可能含私有网络信息，只在本地查看。`127.0.0.53` 只是本地 stub，不是实际上游；继续追到对应链路的 resolver。没有这些工具或相应服务时记录当前管理方式，不为验收安装或切换它们。

`system` / `system://` 不保证内网 DNS。公网系统解析器、缺少 DHCP DNS、多个接口或浏览器独立 DoH 都需按实际路径核实。FlClash 的 macOS 系统 DNS 协调器结论不能直接套用 Windows/Ubuntu。原理见 [DNS 与泄漏模型](dns-and-leak-model.md)。

## TUN、IPv6、WebRTC 与语音

在当前获准模式下，分别检查 IPv4 与 IPv6 的实际应用请求、路由命中和出口；记录 TUN 栈、路由、UDP/TCP DNS 劫持。`any:53` 与 `tcp://any:53` 分别核对。顶层 IPv6 和 `dns.ipv6` 是不同字段；若宿主恢复 IPv6 fake-IP，检查地址池与宽 ULA DIRECT 规则的重叠和顺序，不自动复制拒绝规则。

未启用 TUN 的明确范围可将 TUN 项注明 NOT_APPLICABLE，但不能据此宣称已通过 TUN 验收；WSL/容器或独立核心不替代 Ubuntu 桌面证据。不要为对照关闭现用代理、切换模式、禁用网卡或同时启用两个客户端的 TUN。

WebRTC 使用用户认可、确实工作的测试端点与浏览器，记录 ICE 候选类型（host、srflx、relay）、协议和实际路径。零候选、超时或端点未工作不能判 PASS；srflx/relay 需结合预期策略判断，也不要求所有 IP 与 HTTP 出口字面相同。不要为测试安装扩展、改浏览器策略、阻断全部 UDP 或开启共享 STUN/TURN 捕获。需要语音时另测实际通话建立、收发音频与稳定性；ICE 检查通过不等于通话可用。

## 持久化与离线恢复 {#recovery}

只在已获准刷新订阅或重启客户端时检查持久化，否则记 UNVERIFIED。操作前记录当前可用性、正在使用的客户端/模式、Profile 与脚本绑定、上游选择和本次涉及的每个设置原值，并在本机私密位置保留原始 Profile、脚本及设置备份。预先确认离线可打开备份与客户端；备份中的订阅和凭据不要提交或上传。

恢复卡应在操作前填好，可由用户直接执行：

1. 停止本次验证操作，记录失败步骤；不追加新的网络修改。
2. 在原客户端恢复记录的 Profile、脚本绑定和本次改动字段的原值。需要旧脚本时，从保留的原始 Profile 重新生成，不把旧脚本叠加到新输出。
3. 仅当预先约定时重新加载/重启原客户端；不切到 DIRECT 或另一客户端，不禁用网络。无法恢复时保留现场与错误信息，使用本地备份和原客户端的配置导入入口处理。
4. 复查原业务与 LAN 可用性，记录恢复结果。若本轮只读且未改配置，写“无需恢复”，不虚构恢复已实测。

获准刷新/重启后，重新确认绑定、最终配置、正负样本与 DNS 路径。客户端、核心、脚本、规则来源、订阅组名、GUI 覆写、节点、网络或浏览器 DNS 设置变化后，应复查受影响项目；不自动更新规则或创建定时网络任务。
